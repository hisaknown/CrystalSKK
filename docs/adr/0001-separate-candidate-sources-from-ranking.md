# ADR-0001: 候補の生成と並び替えを別のトレイトに分ける

- ステータス: Accepted
- 日付: 2026-09-22
- 関連: PRD §4 (v2.0) / PRD §7

## 背景

CrystalSKK は当面ふつうの SKK として動けばよいが、最終的には動的補完・予測変換・
文脈を踏まえた候補提示を持たせたい (PRD §4, F-18, F-19)。

素直に書くなら、エンジンは辞書をひとつ持ち、`lookup(key) -> Vec<Candidate>` を呼ぶ。
先行実装の多くもその形に見える。だが後から補完や予測を足すとき、この形だと
「候補をどこから持ってくるか」と「どの順で見せるか」が同じ関数の中で混ざる。

決めるべきは、その混在を最初から避けるかどうかである。

## 選択肢

### A. 辞書をひとつのトレイトにまとめる

`Dictionary::lookup` が候補を順序込みで返す。学習も補完も実装側の中で行う。

- 利点: 型が少ない。初版を書くのが速い。
- 欠点: 補完や予測を足すたびに既存の実装へ手を入れることになる。学習の順序付けと
  候補の出どころが同じ場所に同居し、どちらの都合で書かれたコードか読めなくなる。

### B. 候補ソースとランカーに分ける

`CandidateSource::lookup` が候補を生み、`Ranker::rank` が順序を決める。

- 利点: 「候補を増やす」拡張と「順序を変える」拡張が独立して足せる。動的補完は
  前者、学習と文脈スコアリングは後者として、互いに知らずに共存できる。
- 欠点: 型と呼び出しが一段増える。初版では `NoopRanker` しか存在せず、分割の
  効果がしばらく見えない。

### C. 後で分ける

まず A で書き、賢い候補提示に着手する段になって B へ移す。

- 利点: 今は最短で進める。
- 欠点: 移行時にエンジンと全辞書実装を同時に書き換えることになる。その頃には
  TIP とサーバーが上に乗っており、書き換えの影響範囲が最も大きい時期に当たる。

## 決定

**B を採る。** 候補の生成と並び替えを `CandidateSource` と `Ranker` に分け、
変換時の周辺情報を `Context` として両者に渡す。

C を採らないのは、分割のコストが今はほぼゼロである一方、後回しにすると最も高く
つくため。B の欠点である「しばらく効果が見えない」は、実装量としては
`NoopRanker` ひとつぶんでしかない。

`Context` には、取得できないことがある項目 (周辺テキスト、アプリケーション識別子)
を最初から含めておく。PRD §3 の「入力を止めない」に従い、これらが欠けても
ランカーは機能を落とすだけで動作しなければならない。

## 帰結

- 補完・予測変換・skkserv は、エンジンに手を入れず `CandidateSource` の追加で足せる。
- 学習と文脈スコアリングは `Ranker` の差し替えで足せる。
- 候補ソースは「自分にとって自然な順」で返せばよく、順位付けの責任を負わない。
  複数ソースの合成 (`ChainedSource`) は重複除去だけを行う。
- 一方で、**ソースをまたいだ順位付けはランカーにしかできない**。ユーザー辞書を
  常に優先したい、といった要求はソースの並び順ではなくランカーで表現することになる。
  ここは直感に反しうるので、実装時に迷ったらこの ADR に戻ること。
