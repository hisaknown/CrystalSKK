# ADR-0003: 内部表現とユーザー辞書を UTF-8 に統一し、EUC-JP は読み込み時に変換する

- ステータス: Accepted
- 日付: 2026-09-22
- 関連: PRD §12 Q-07 / PRD N-10 / PRD F-09

## 背景

配布されている SKK 辞書の多く (SKK-JISYO.L を含む) は EUC-JP である。歴史的な
経緯によるもので、ddskk をはじめ既存の実装はこの文字コードのまま扱ってきた。

一方 CrystalSKK の内部表現は Rust の `String`、すなわち UTF-8 である。Windows の
ファイルパスとテキスト入力も UTF-16 と UTF-8 の世界にある。どこかで必ず変換が
起きるので、それを**どこで一度だけ行うか**を決める必要がある。

ユーザー辞書は他の SKK 実装と行き来できることが要件なので (PRD N-10)、
保存する文字コードの選択は互換性に直接響く。

## 選択肢

### A. EUC-JP のまま扱う

辞書は EUC-JP のバイト列として保持し、検索もバイト列で行う。

- 利点: 既存の辞書とユーザー辞書をそのまま読み書きできる。変換が要らない。
- 欠点: 内部のあらゆる文字列操作に変換が必要になり、変換が毎回の検索に散らばる。
  EUC-JP で表現できない文字 (絵文字など) を登録できない。

### B. 内部は UTF-8、ユーザー辞書は読み込んだ文字コードで保存する

- 利点: 既存のユーザー辞書を文字コードごと保ったまま更新できる。
- 欠点: 保存のたびに変換が要る。EUC-JP にできない文字を登録したとき、
  保存できずに学習が失われる。しかもそれは**登録した後**に分かる。

### C. 内部もユーザー辞書も UTF-8。読み込みのときだけ変換する

- 利点: 変換が読み込みの一点に閉じる。表現できない文字が原理的に存在しない。
- 欠点: EUC-JP のユーザー辞書を引き継ぐと、次の保存で文字コードが変わる。
  古い実装と同じファイルを共有している利用者には非互換になりうる。

## 決定

**C を採る。** 内部表現とユーザー辞書の保存は常に UTF-8。EUC-JP の辞書は
読み込み時に一度だけ変換する。静的辞書はダウンロード時に変換して保存する。

決め手は B の欠点で、**学習を失う可能性があること**。PRD §3 の「ユーザーのデータは
ユーザーのもの」に反する。保存できない文字があるという制約を、利用者が登録操作を
終えてから知ることになるのは受け入れられない。

C の非互換は、書き出すファイルの先頭に `coding: utf-8` を明記することで緩和する。
ddskk はこの指定を読むため、文字コードが変わっても読める。

文字コードの判定は、先頭の注釈行の `coding:` 指定、UTF-8 としての妥当性、
EUC-JP の順で行う。SKK 辞書は先頭に `;; -*- coding: euc-jp -*-` を持つのが
慣例なので、多くは一つ目で決まる。

変換には `encoding_rs` を使う。純 Rust であり、PRD N-08 を破らない。

## 帰結

- 絵文字を含む任意の文字を辞書登録できる。
- 変換は読み込みの一点にしかないので、検索の速度に影響しない。
- **EUC-JP のユーザー辞書を他の実装と共有している利用者には、非互換が起きる。**
  移行時に警告を出すことを設定 UI 側の要件とする。
- 書き出しの並び順は UTF-8 のバイト順になる。慣例の辞書は EUC-JP のバイト順で
  並んでいるため、ASCII とかなが混在する位置での順序が異なる。全件を走査する
  読み手には影響しないが、二分探索で読む実装に自前のユーザー辞書を渡す場合は
  注意が要る。
- BOM の扱いは UTF-8 のものだけを取り除く。EUC-JP の辞書の先頭バイトが偶然
  UTF-16 の BOM と一致したときに、辞書全体を取り違えないようにするため。
