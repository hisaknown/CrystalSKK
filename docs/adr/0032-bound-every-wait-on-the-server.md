# ADR-0032: 辞書サーバを待つ時間には、どこでも上限を設ける

- ステータス: Accepted
- 日付: 2026-09-24
- 関連: PRD §3, ADR-0016

## 背景

TIP は入力先アプリの UI スレッドから辞書サーバに頼む (ADR-0016)。待って
いるあいだ、**アプリは固まる**。

- パイプで待つ時間には、繋ぐところにしか期限 (200 ms) がなかった。繋がった
  あとにサーバが忙しいと、答えが来るまでいくらでも待った。サーバは一件ずつ
  順に答えるので、別のアプリの変換 (並べ替えのある変換は時間がかかる) の
  後ろに並ぶこともある。スタートメニューの検索欄が数秒固まることがあった。
- サーバが居なければ起こし、決め打ちで 300 ms 寝てから尋ね直していた。
  ログオン直後は、ログオンで起こしたサーバがまだ辞書を読んでいてパイプが
  開いていない。そこで有効化されたアプリは「起こす、寝る、繋がらない」を
  二度繰り返し、UI を 0.8 秒ほど止めていた。
- サーバが居ないのは、ログオン直後と、導入や更新で入れ替えている最中くらい
  である。本当に落ちることはまずない。

## 選択肢

### A. 頼みの種類ごとに期限を分ける

- 利点: 並べ替えのある変換にだけ長めの時間を許せる。
- 欠点: 数字が増える。狙いは異常なときに止まり続けないことで、普段の
  答えは数ミリ秒で返るので、分けても得るものが少ない。

### B. 一律の期限を設け、起動待ちは短い間隔で試し直す

- 利点: 数字は二つだけで済む。早く起きればすぐ抜ける。
- 欠点: 期限を越えた答えは捨てる。

### C. UI スレッドで待たない (別の糸で頼む)

- 利点: アプリを止めない。
- 欠点: TSF の呼び出しは同期で答えを返す作りで、候補を後から差し込む
  仕組みを作り直すことになる。今の症状に比べて大がかりすぎる。

## 決定

B を採る。PRD §3「ホストアプリを巻き込まない」を、上限のある待ちとして守る。

- **一つの頼みは、繋ぐ・送る・受け取るを合わせて 500 ms で打ち切る。**
  頼みの種類は区別しない。
- **起こすのは「居ない」(パイプが無い) ときだけにする。** 居るのに答えない
  なら、起こしても尋ね直しても直らず、待ちが重なるだけになる。
- 起こす前に、サーバの名乗り (ミューテックス) を見る。名乗りがあれば起き
  かけているので、もう一つは起こさない。CorvusSKK も同じ確かめ方をする。
- **起こしたあとは寝ない。** 20 ms おきに繋ぎに行き、1000 ms で諦める。
  パイプが無いうちは繋ぎに行ってもすぐ断られるので、叩いても軽い。指数的に
  間隔を広げないのは、相手が混んでいるのではなく、起きるのを待っているだけ
  だからである。1000 ms と長めにしたのは、めったに払わないためで、払うなら
  その変換で候補が出るほうがよい。
- 答えが来なかった学習は送り直さない。届いてはいるかもしれず、二重に覚え
  させるより一度落とすほうが害が小さい。

期限を越えたときの扱いは、これまでの「繋がらない」と同じにする。変換なら
「辞書に繋がりません」を出し、次に頼んだときにまた繋ぎに行く。設定なら前に
受け取った値で続ける。

## 帰結

- アプリが固まる時間には上限ができる。一つの頼みで最悪 1.5 秒ほど (起動を
  待ち、繋がった直後にサーバが忙しい場合)。普段は数ミリ秒で変わらない。
- 並べ替えに 500 ms 以上かかる環境では、変換が「繋がりません」になる。
  そうなったら、並べ替えを切るか、期限を見直す。
- まだ、焦点が移るたびに設定を問い合わせている。利用者が何もしていなく
  ても、そこで待ちが起きうる。これは別に決める。
