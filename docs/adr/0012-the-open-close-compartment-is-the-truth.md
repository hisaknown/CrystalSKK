# ADR-0012: 入力方式の入切は向こうが決める

- ステータス: Accepted
- 日付: 2026-09-22
- 関連: ADR-0010 (一部を覆す), ADR-0011

## 背景

Claude Desktop の入力欄で、日本語が一文字も打てなかった。英数字がそのまま
入るだけで、`Ctrl+J` も効かない。ブラウザやメモ帳では問題がない。

ログを整え、時刻とアプリ名を入れ、包装されたアプリ向けの逃げ道まで足した。
**それでも症状の原因は出てこなかった。** 道具を磨く方向へ進みかけたところで、
CorvusSKK と突き合わせるべきだという指摘を受けた。決まりきった書き方の部分に
独自性は要らない。

突き合わせて、すぐに見つかった。CorvusSKK が打鍵を食べるか決める関数は、
こう始まる。

```cpp
BOOL CTextService::_IsKeyEaten(ITfContext *pContext, WPARAM wParam)
{
    if (_IsKeyboardDisabled()) return FALSE;
    if (!_IsKeyboardOpen())    return FALSE;
```

**入切の区画を読んでいる。** こちらは書くだけで、一度も読んでいなかった。

## 問題

ADR-0010 で、入力モードから入切を導いて書くことにした。半角英数なら切、
それ以外なら入、と。**これが誤りだった。**

入切は入力モードとは別の軸で、しかも**持ち主が違う**。

- 利用者が入切のキーを押せば Windows が書く
- アプリが自分の都合で入力方式を切りたければアプリが書く

こちらが書いた値がそのまま残っている保証はない。Claude Desktop で起きて
いたのはまさにそれで、入力欄が切にしたまま、こちらはそれを知らずに
「ひらがなのつもり」でいた。**打鍵は届いていなかった。**

そして届かないのだから、`Ctrl+J` も届かない。入に戻す手立てが無い。

## 決定

**区画が本当で、こちらが従う。**

1. 打鍵を食べる前に入切を読む。切なら食べない。入力先が文字を断って
   いるとき (`KEYBOARD_DISABLED`, `EMPTYCONTEXT`) も食べない
2. 入切の変化を知らせてもらう (`ITfCompartmentEventSink`)。入にされたら
   ひらがなで始め、切にされたら途中経過を捨てる
3. **入切のキーを横取りする** (preserved key)。半角/全角、Alt+`、IME 専用の
   キー。切られているとき打鍵は届かないので、これが唯一の戻り道になる
4. 入力モードを掲示するとき、入切には触れない

読めないときは切とみなす。入っていると決めてかかって打鍵を食べると、
**文字がどこにも行かないまま消える**。分からないなら素通しするほうが害が
小さい。

## 帰結

- ADR-0010 の「入力モードから入切を導いて書く」は撤回する。同 ADR の
  入力モードの掲示は残る。
- 入と切、どちらの状態も CrystalSKK は持たない。区画を読む。**二箇所に
  状態があると必ずずれる。**
- 半角英数 (`l`) は「入だが英数」であり、切ではない。利用者にとっても
  この二つは別物で、`l` で抜けた先は `Ctrl+J` で戻れる場所である。
- 横取りキーは入と切の両方に同じ組み合わせを登録する。同じキーが入切を
  兼ねるため。
- **症状が出ないアプリで確かめていると、抜けに気づけない。** メモ帳が
  たまたま入にしていたせいで、読んでいないことが半月ぶんの実装のあいだ
  表に出なかった。決まりきった部分は、動くものに倣うのが速い。
