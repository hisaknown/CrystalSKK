# ADR-0015: 候補一覧は自前で描き、同時に差し出す

- ステータス: Accepted
- 日付: 2026-09-23
- 関連: PRD Q-02, ADR-0011

## 背景

PRD Q-02 は「候補ウィンドウを自前描画にするか、TSF の UI Element に委ねるか」
という二択として書かれていた。

**二択ではなかった。** CorvusSKK の `CandidateUIElement.cpp` を開くと、中身は
自前で描く窓と同じオブジェクトが `ITfCandidateListUIElement` を実装している。
両方やっている。

理由は、二つが別のことを担っているためである。

- **自前描画** … 普通のアプリでは、これが無いと候補が一つも見えない
- **UI Element** … 「候補一覧を持っている」という申告。アプリが自分で描くと
  言ってくることがあり、そのときは中身を渡す口になる

片方だけでは必ず穴が開く。

## 決定

**両方を持ち、申告の答えで描く側を決める。**

一覧を開くとき `BeginUIElement` で申告する。返ってきた答えが「自前で描け」
なら窓を出し、「こちらで描く」なら窓は出さず中身だけを渡す。どちらでも、
変わるたびに `UpdateUIElement` で知らせ、閉じたら `EndUIElement` で畳む。

渡すのは**一覧に載る候補だけ**である。一つずつ見せていた最初の数件を混ぜると、
ページの区切りが合わなくなる (ADR は無いが `CandidateView::listed` がその境)。

アプリからのページ送り (`SetPageIndex`) は受け付けない。**ページを送るのは
打鍵であってエンジンの状態**で、外から動かされると一覧と `▼` の見出しが
食い違う。

## 窓にはアプリの窓を親として与える

ストアアプリで、申告も窓の作成も成功しているのに何も見えない、という状態に
なった。窓は出来ていた。**アプリの描画面の下にいた。**

オーナーの無いポップアップには、上に重なるべき相手がない。`ITfContextView::GetWnd()`
でアプリの窓を取り、取れなければ焦点のある窓で代えて、それをオーナーにする。
CorvusSKK も同じ手順を踏んでおり、あちらは**オーナーが取れなければ窓を作らない**
ほど、これを前提にしている。

## 帰結

- PRD Q-02 は解決。「どちらか」ではなく「両方」が答えだった。
- 分類に `UIELEMENTENABLED` を名乗っていたのは、本 ADR の実装までは
  **中身のない名乗り**だった。ADR-0011 に「できないことを名乗っても仕方が
  ない」と書いた、その逆の状態がしばらく続いていたことになる。
- 「作ったのに見えない」は「作れていない」とは別の症状である。**記録に
  成功が並んでいるのに見えないなら、置き場所と重なり方を疑う。**
