# ADR-0004: 辞書の取得に OS の HTTP スタック (WinHTTP) を使う

- ステータス: Accepted
- 日付: 2026-09-22
- 関連: PRD N-08 / PRD F-10 / PRD §10

## 背景

CrystalSKK は辞書を同梱せず、利用者の操作で HTTPS 越しに取得する (PRD §10)。
つまり TLS クライアントが要る。

一方で PRD N-08 は「C ツールチェインを要求しない」と定めている。ここが衝突する。
Rust の標準的な HTTPS クライアントは `rustls` を使うが、**`rustls` の暗号実装は
既定でも代替でも C とアセンブリを含む**。`aws-lc-rs` も `ring` も `cc` crate
経由で C をビルドするため、どちらを選んでも N-08 を破る。

## 選択肢

### A. rustls を使い、N-08 を緩める

「TLS の部分だけは C のビルドを許す」と例外を設ける。

- 利点: 素直。エコシステムの主流に乗れる。
- 欠点: N-08 の目的は「clone して `cargo build` だけで済むこと」なので、
  例外を一つ設けた時点でその保証が消える。しかも辞書取得という周辺機能の
  ために、プロジェクト全体の性質を変えることになる。

### B. `native-tls` を使う

Windows では schannel を呼ぶため、C のビルドは発生しない。

- 利点: 変更が小さい。Windows では OS の TLS を使える。
- 欠点: Windows 以外では openssl に落ちるため、CI の検査 (Linux 上で
  `cargo tree --invert cc`) が通らなくなる。「Windows 用だから」で
  検査を弱めると、N-08 の担保そのものが形骸化する。

### C. OS の HTTP スタック (WinHTTP) を直接呼ぶ

`windows` crate 経由で WinHTTP を使い、HTTP と TLS の両方を OS に任せる。

- 利点: 依存が増えない (`windows` crate は TIP でどのみち要る)。C のビルドは
  発生しない。証明書の検証、証明書ストア、**システムのプロキシ設定**がすべて
  Windows のものになる。企業環境のプロキシ配下で動くことは実利が大きい。
- 欠点: `unsafe` を書くことになる。Windows 専用になる。HTTP の細かい制御や
  再試行の挙動を自分で用意する必要がある。

## 決定

**C を採る。**

決め手は、我々が作っているのが**そもそも Windows 専用のソフトウェアである**こと。
TLS スタックを自前で抱えることは、OS が同じ機能を提供している以上、証明書ストアと
プロキシ設定を二重に持つことを意味する。企業環境での「IME は動くが辞書だけ
落とせない」という失敗を避けられる点でも、OS に任せるほうが正しい。

N-08 は「例外なく守る」から意味がある制約だと考える。A と B はどちらも例外を
作る案であり、一度作れば次も作ることになる。

`unsafe` は `winhttp.rs` 一ファイルに閉じ込める。ワークスペース全体では
`unsafe_code = "deny"` を維持し、このクレートだけで緩める。

## 帰結

- 依存ツリーに暗号ライブラリが現れない。`cargo tree --invert cc` の検査を
  例外なく維持できる。
- プロキシ、証明書ストア、TLS のバージョン更新はすべて Windows に追従する。
  こちらで面倒を見る必要がない。
- 取得部分は Windows 専用になる。変換と保存 (`install_bytes`) は通信を含まない
  関数として切り離してあり、他の環境でも試験できる。
- `unsafe` が入る最初のクレートになる。TIP も同じ性質を持つので、ここでの
  書き方 (ハンドルを `Drop` を持つ型で包む、`SAFETY` 注釈を残す) を
  そのまま踏襲する。
- HTTP の再試行、進捗表示、帯域制限は自前で用意することになる。現時点では
  どれも未実装。
