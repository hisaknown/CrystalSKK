# ADR-0042: 辞書の候補が尽きたら、ネットの候補を出す

- ステータス: Accepted
- 日付: 2026-10-23
- 関連: PRD §3, ADR-0001, ADR-0004, ADR-0016, ADR-0025, ADR-0032

## 背景

辞書に無い語は、辞書登録で一から打つしかない。新しい言葉や固有名詞ほど
そうなり、打つ手間がいちばんかかる場面でもある。

かな漢字変換を返すウェブの API がある。Google CGI API for Japanese Input
(`https://www.google.com/transliterate`) は鍵が要らず、読みを送れば候補が
JSON で返る。ただし**提供が続く保証はない**。

前提になる事実:

- 辞書を持つのは `crystalskk-server` だけで、TIP は名前付きパイプで頼む
  (ADR-0016)。境目は `CandidateSource` である (ADR-0001)。
- TIP は入力先アプリの UI スレッドでサーバを待ち、一つの頼みは 500 ms で
  打ち切る (ADR-0032)。サーバは頼みを一件ずつ順に答える。
- HTTPS は WinHTTP で、辞書の取得にもう使っている (ADR-0004)。
- 読みを外へ送ることになる。IME がそれをすると、打った文字を外に漏らす
  ものと受け取られても仕方がない。

## 選択肢

### A. 別プロセスの skkserv を立て、TIP がそれに尋ねる

SKK で古くからあるやり方。`yaskkserv2` などに Google の変換を引く機能がある。

- 利点: 既存の実装を使える。ネットに出る処理を TIP の外へ置ける。
- 欠点: **TIP の外へ置くことは、辞書サーバがもう満たしている。** 待ち合わせ
  の相手が二つになり、起こす・待つ・諦めるを二通り持つことになる。

### B. 辞書サーバがウェブの API を引き、ふつうの辞書と並べて引く

- 利点: いちばん素直。
- 欠点: **変換のたびに外へ尋ねる。** 答えを待てばどの変換も遅くなり、待た
  なければ並びが毎回揺れる。辞書にある語の読みまで外へ送ることになる。

### C. 辞書サーバがウェブの API を引くが、候補が尽きたときだけ尋ねる

辞書の候補を出し切ったとき (と、一件も無いとき) にだけ尋ね、返ってきた
ものを候補の後ろに付け足す。取得はサーバの裏で進め、頼みにはすぐ答える。

- 利点: ふだんの変換は今と変わらない。外へ送るのは、辞書に無かった読み
  だけになる。
- 欠点: 最初の一回は答えが間に合わない。そのあいだ何かを見せ、もう一度
  尋ねる仕組みが要る。

## 決定

C を採る。PRD §3「ホストアプリを巻き込まない」を守ったまま、辞書登録の
手前に一段足す。

### サーバ

- **ネットの候補は、辞書と同じく辞書サーバだけが引く。** 新しい頼み
  `web` を足す。TIP はインターネットに出ない。
- 頼まれたら、すぐに次のどれかで答える。**外の API の答えを待たない。**
  待てばパイプの列が塞がり、ほかのアプリの変換まで止まる (ADR-0032)。
  - 取れている: 候補 (辞書にもある語は除く)
  - 取れたが無かった: 空の候補
  - 取りに行っている: `pending`
  - 使わない設定: `error`
- 取りに行くのは裏のスレッドで、取れたものは読みごとに覚えておく。
  **無かったことも覚える。** 二度目からは外へ出ない。覚えるのはサーバが
  動いているあいだだけで、ファイルには書かない。
- 取れなかったとき (繋がらない、答えが読めない) も「無かった」と同じに
  扱い、記録に残す。辞書登録へ進めなくなるより、登録できるほうがよい。
- 外へ送るのは読みだけで、前後の文章は送らない。
- 既定では使わない (`[web] enabled = false`)。

### エンジン

`CandidateSource` に `lookup_web` を足す。既定は「使わない」。

- **候補を送り切ったとき**、辞書登録へ進む前に尋ねる。
  - 候補が来たら、後ろに付け足してそこへ進む。
  - `pending` なら、いまの候補に留まる。
  - 無い、または使わないなら、今までどおり辞書登録へ。
- **辞書に一件も無かったとき**も同じ。`pending` なら見出し語入力に留まる。
- **先には尋ねない。** 尋ねるのは、今までなら辞書登録に入っていた打鍵で
  ある。

  初めは最後のページ (一つずつ見せているなら最後の一件) に来た時点で先に
  尋ねていた。送ったときに候補が並んでいるようにするためだったが、候補が
  一つきりの変換や動的補完で受け取った変換では、**変換した途端に「取得中」
  が出た。** 出るかどうかが辞書の中身で決まり、利用者には脈絡なく見えた。
- 一つの変換で「無い」と言われたら、その変換ではもう尋ねない。

`pending` で留まったときは、**届いたら何をするか**を覚えておく (変換し直す
か、送る)。TIP は待っているあいだ 100 ms おきに `poll_web` で
尋ね直し、届いたら、エンジンは待たせた打鍵の続きをする。利用者がもう一度
送る必要はない。届いて何も無ければ、その打鍵で起きるはずだったとおり
辞書登録へ進む。打鍵があれば待つのをやめ、10 秒待っても届かなければ
尋ねるのをやめる。

尋ね直すのは窓を持たないスレッドの時計で、打鍵を受けたのと同じスレッドで
鳴る。一回ごとの待ちは ADR-0032 の上限の中に収まる。

並びは辞書が先、ネットが後で、ランカーはネットの候補に触れない。ネットの
候補を選べば、ほかの候補と同じく学習としてユーザー辞書に入る。次からは
辞書の候補になる。

### 見せ方

- ネットの候補には、注釈として `🌐` を付ける。
- 取りに行っているあいだは、**候補の窓**に `🌐 取得中…` を出す。一覧が
  出ていればその末尾に一行足し、出ていなければ (一つずつ見せている段階、
  辞書に一件も無く見出し語入力のまま) それだけの窓を出す。候補を取って
  いるのだから、候補の窓で言う。

  初めはカーソルのそばのモードの窓 (ADR-0025) に地球儀の絵を出していた。
  どの場面でも出せるからだったが、入力モードの知らせと見分けがつかず、
  候補とも結び付かなかった。

## 帰結

- 辞書に無い語でも、打たずに選べることが増える。選べば辞書に残る。
- 届いたら、時計で書き換えるので、打鍵の外で文書を書き換えることになる。
  打鍵のときと同じ同期の編集セッションを頼む。断るアプリでは、届いても
  見え方が変わらない (次の打鍵で映る)。
- 裏の取得には期限を設けていない。WinHTTP の既定の期限で諦めるまで、
  その読みは `pending` のままになる。困るようなら期限を足す。
- 使う API は一つに決め打ちしてある。提供が終われば、この機能は「無かった」
  を返し続けるだけで、入力は止まらない。そのときは別の API を足す。
- 候補の窓の `🌐` は文字であり、絵ではない。書体によっては白黒で出る。
