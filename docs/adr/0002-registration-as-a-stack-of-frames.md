# ADR-0002: 辞書登録を第四の状態ではなく枠のスタックとして表現する

- ステータス: Accepted
- 日付: 2026-09-22
- 関連: PRD §5.1 (F-07) / CONTEXT.md「辞書登録」

## 背景

SKK では候補が尽きると辞書登録に入る。登録中の入力は通常の入力とまったく同じに
振る舞い、そこでさらに変換ができる。その変換でまた候補が尽きれば、登録の中で
登録が始まる。つまり**辞書登録は原理的に入れ子になる**。

状態機械を「直接入力・見出し語入力・候補選択・辞書登録」の四状態として書くと、
この入れ子を表現できない。登録状態の中に完全な状態機械がもう一つ必要になる。

## 選択肢

### A. 辞書登録を第四の状態にする

`State::Registering` が内部に入力バッファと、入れ子のための状態を持つ。

- 利点: 「登録中である」ことが状態として明示される。
- 欠点: 登録状態の中で直接入力・見出し語入力・候補選択をすべて再現する必要がある。
  同じ遷移規則が二箇所に書かれ、片方だけ直す事故が起きる。

### B. エンジンを入れ子にする

登録に入ったら新しい `Engine` を作り、その確定出力を親が受け取る。

- 利点: 遷移規則の重複がない。
- 欠点: 辞書・ランカー・設定・入力モードを子と共有する必要があり、所有権の設計が
  重くなる。入れ子の深さだけエンジンが増える。

### C. 直接入力の上に積む枠として表現する

状態は三つのまま。登録に入ったら `Registration` という枠をスタックに積み、
状態は直接入力へ戻す。枠が積まれている間、**確定した文字列はアプリではなく
枠のバッファへ流れる**。

- 利点: 遷移規則は一組だけ。入れ子は `Vec` が深くなるだけで、状態機械は何も
  知らなくてよい。
- 欠点: 「今は登録中である」が状態を見ても分からず、スタックの有無で判断する。
  確定の宛先が状況によって変わる。

## 決定

**C を採る。**

決め手は、A と B がどちらも「入力の振る舞いは登録中も変わらない」という SKK の
性質を、構造として表現できていないこと。登録中の入力が通常の入力と同じなら、
状態機械も同じものであるべきで、違うのは**確定した文字列の行き先だけ**である。
C はその違いだけを実装している。

確定の宛先が変わる点は、`Engine::emit` 一箇所に閉じ込めることで扱う。

## 帰結

- 入れ子の深さに制限がない。深さは `registration_depth()` で外から観測できる。
- 登録中も入力モードの切り替え、候補選択、暗黙の確定がそのまま使える。
  これらを別途実装する必要がない。
- 確定文字列がアプリへ届くかどうかは `emit` の中でしか決まらない。エンジンに
  出力経路を増やすときは、必ず `emit` を通すこと。直接 `Response::commit` へ
  書くと、登録中の入力がアプリへ漏れる。
- 「登録中」は状態ではないため、状態を見るだけのコード (preedit の描画など) は
  スタックも併せて見る必要がある。`Preedit::registering` がそのために存在する。
