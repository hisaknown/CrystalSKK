# ADR-0028: 小窓は出すモニターの拡大率で描き、入力先の組版の変化に付いていく

- ステータス: Accepted
- 日付: 2026-09-23
- 関連: ADR-0015, ADR-0025, ADR-0026

## 背景

二つの不具合があった。

- **拡大率の違うモニターで、小窓の大きさが違って見えた。** 候補の窓とモードの
  窓は、システムの拡大率で一律に描いていた。たとえば 150% のモニターと 100% の
  モニターを並べると、片方では大きすぎ、もう片方では小さすぎた。
- **ブラウザなどで、窓の位置がずれた。** 位置は打鍵のときに一度だけ尋ねていた。
  ブラウザは打鍵の直後にはまだ組版を終えておらず、そのときの位置は古い。
  スクロールしたり窓を動かしたりしたときも、小窓は元の場所に残った。

## 決定

### 拡大率

**小窓は、それを出すモニターの拡大率で描く。** ただし小窓は入力先アプリの
プロセスの中で作られるので、そのアプリの拡大率の扱いに合わせる (`dpi.rs`)。

- モニターごとの拡大率に対応したアプリ: そのモニターの拡大率
  (`GetDpiForMonitor`) で描く。
- システムの拡大率にだけ対応したアプリ: システムの拡大率で描く。モニターの
  違いは Windows が伸縮して吸収する。
- どちらにも対応しないアプリ: 100% で描き、Windows に伸ばしてもらう。

**アプリの扱いを確かめずに決めると、二重に伸びる。** 書体も
`SystemParametersInfoForDpi` で、その拡大率の大きさで作る。

### 位置

**小窓を出しているあいだ、入力先の組版の変化 (`ITfTextLayoutSink`) を聞く。**
CorvusSKK が候補の窓とモードの窓でしていることと同じである。

- 変化 (`TF_LC_CHANGE`) の知らせが来たら、読むだけの編集セッションで位置を
  尋ね直す。候補の窓なら未確定の文字列、モードの窓ならカーソルの位置を使う。
  そして中身は変えずに窓だけを動かす。動いた先で拡大率が変われば、その
  大きさで描き直す。
- 入力先の画面が消えた (`TF_LC_DESTROY`) ら、窓を隠して聞くのをやめる。
- **未確定の文字列があるあいだは、窓が出ていなくても聞き、知らせが来たら
  尋ね直す。** Firefox は組版を聞く相手がいると、組み終えるまで位置を答えず、
  組み終えてから知らせてくる。打鍵のときに位置が取れず、出せなかった窓は、
  この知らせで出す。窓が出ているときだけ聞く作りにしたところ、Firefox で
  候補の窓も注釈の窓も出なくなった。
- 聞くのは一度に一つの入力先だけにする。焦点が移ったときと無効化のときにも
  やめる。どの窓も出ていないのに知らせが来たら、その場でやめる。

辞書登録中は文書に未確定の文字列が無いので、尋ね直す相手がいない。候補の窓は
最後に分かった場所に留まる。

### 位置を答えないアプリ

TSF で位置を尋ねても答えないアプリがある。そのときは **Windows が覚えている
キャレットの位置 (`GetGUIThreadInfo`)** を使う。TSF には答えなくても、読み上げ
ソフトのためにキャレットを作っているアプリは多い。キャレットは未確定の文字列の
末尾にあることが多いので、窓は少し右にずれる。それでも、窓が出ないよりはよい。

## 帰結

- 組版の知らせはアプリ次第である。知らせを出さないアプリでは、これまでどおり
  打鍵のときの位置に出る。
- 編集セッションは非同期で頼む (`TF_ES_ASYNCDONTCARE`)。知らせの中から同期で
  頼むと断られることがある。窓が動くのは知らせより少し後になる。
