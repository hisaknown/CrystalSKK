# ADR-0030: 候補の並びを、サーバに常駐させた小さな言語モデルで文脈から決める

- ステータス: Accepted
- 日付: 2026-09-23
- 関連: ADR-0001, ADR-0016, ADR-0019, ADR-0020, PRD §3, PRD F-19

## 背景

候補はいま辞書の順に出ている。学習した語が先頭に来るほかは、前後に何が
書いてあっても並びは変わらない。

ブランチ `experiment/llm-ranking` の `experiments/ranking/` で、小さな言語モデルに
候補を採点させる実験をした (master には入れていない)。
問題はこのリポジトリの日本語 (どのモデルの学習時期よりも新しい) から作った
送りなしの変換 1000 問で、辞書は SKK-JISYO.L である。

- 採点は生成ではない。「前の文章 + 候補 + 後ろの文章」の同時確率を候補ごとに
  求め、比べる。全候補に共通する先頭の KV キャッシュを共有し、残りの
  数トークンだけを一つのバッチで流す。トークンの切れ目と候補の切れ目は
  揃っていなくてよい。
- 辞書順のままだと第一候補の正解率は 0.884 である。言語モデルの対数尤度に
  辞書順の重み (−λ·log 順位) を足すと、次のようになった。
  llama.cpp の Q4_0、候補 7 個、CPU 8 スレッド (Ryzen 7 7700) での値。

  | モデル | 大きさ | 後ろの文章 | 正解率 | 候補の採点 | 前の文章の計算 |
  |---|---|---|---|---|---|
  | llm-jp-3-150m | 84 MB | なし | 0.949 | 2.7 ms | 16 ms |
  | llm-jp-3-150m | 84 MB | 5 文字 | 0.974 | 6.8 ms | 16 ms |
  | llm-jp-3-440m | 242 MB | なし | 0.969 | 8.0 ms | 64 ms |
  | llm-jp-3-440m | 242 MB | 5 文字 | 0.978 | 20 ms | 63 ms |
  | sarashina2.2-0.5b | 428 MB | 5 文字 | 0.976 | 43 ms | 123 ms |

- 大きいモデルは要らない。遅延はほぼ重みの読み出しと候補部分のトークン数で
  決まる。エンコーダ (ModernBERT 系) の pseudo-log-likelihood は珍しい漢字に
  引かれ、辞書順より悪かった。
- 残った誤りの多くは「受け取り/受取」のような表記の揺れで、文脈では決まらない。
  書き手の好みであり、学習が受け持つべきものである。
- 文章の末尾に書き足していくのがふつうの打ち方なので、後ろの文章は無いことが多い。

構造の上では、エンジンは TIP (各アプリのプロセス) にあり、辞書はサーバにある
(ADR-0016)。`Ranker::rank` はエンジンが変換のときに同期で一度だけ呼ぶが、
いまは `NoopRanker` しか無い。`Context` の周辺テキストはどこからも埋められて
おらず、TIP は文書の文字を読んでいない。サーバから TIP へ知らせる道は無い。

## 選択肢

### A. TIP のランカーから、並べ替えだけをサーバへ頼む

`Ranker` を実装した `RemoteRanker` を TIP に置き、辞書引きとは別の要求で
並びをもらう。

- 利点: エンジンの呼び出し順をそのまま使える。
- 欠点: 変換のたびにパイプの往復が二度になる。学習した語かどうかは
  サーバしか知らないので、その印も運ぶ必要がある。

### B. サーバで辞書を引くついでに並べる

変換の `search` 要求に周辺テキストを添え、サーバは候補ソースを引いたあと
その場でランカーを通して返す。TIP のランカーは `NoopRanker` のままにする。

- 利点: 往復は一度で済む。学習の履歴も言語モデルもサーバに一つだけあり、
  アプリごとにメモリを使わない。TIP に持たせる状態が増えない。
- 欠点: 周辺テキストを候補ソースの問い合わせに乗せる口が core に要る。

### C. 言語モデルを使わず、統計で並べる

利用者の確定履歴から「直前の語 → 選んだ候補」を数える。

- 利点: 軽い。
- 欠点: 使い始めは何も知らない。コーパスから作るなら、データと学習の
  手間がかかる。言語モデルはそのどちらも要らない。

## 決定

**B を採る。** サーバに小さな言語モデルを常駐させ、変換の問い合わせで
辞書を引いたあと、その場で並べて返す。

- `Ranker` は core に残す。サーバの `Library` が「候補ソース → ランカー」と
  組み立てる (ADR-0001 の分け方はそのまま)。
- **周辺テキストが添えられた問い合わせだけを並べる。** 補完のプレビューや
  語の有無の確認でも辞書は引かれるが、そこで言語モデルは回さない。
- **並べ方**: 言語モデルの対数尤度に辞書順の重み (−λ·log 順位) を足した値で
  並べる。**最後に使った語 (学習で先頭に来た語) は、先頭から動かさない。**
  利用者の手癖を壊さないためで、表記の揺れもここで片付く。
- **締め切りを持つ。** 採点が決めた時間で終わらなければ辞書の順で返す。
  言語モデルが無い、読み込めない、壊れているときも同じで、入力は止めない
  (PRD §3)。
- **TIP が周辺テキストを取る。** 変換を始めるときに、カーソルの前後の文字を
  TSF で読んでエンジンの `Context` に入れる。**パスワード欄 (InputScope) では
  読まない。** 取れないアプリでは直近の確定文字列で代える。周辺テキストは
  記録に残さず、保存もしない。
- **llama.cpp は、公式のビルド済み DLL を動的に読む。** C++ をビルドしない。
  使う関数だけ FFI を手で書き、対応する llama.cpp の版を固定する。
- **トークン化は Rust の `tokenizers` で行う。** llm-jp の語彙は llama.cpp が
  正しく扱えないためで、GGUF の語彙は読み込みを通すためだけに持たせる。
- 既定のモデルは llm-jp-3-150m と llm-jp-3-440m のどちらかとし、差し替え
  られるようにする。どちらにするかは使いながら決める。
- 設定に `[ranker]` を足す (有効か、モデル、λ、締め切り、前後の文章を何文字
  渡すか)。ADR-0020 に従い既定値もテンプレートに書く。実験は前の文章 200 文字
  で行ったが、そこまでは要らないと見て、既定は短めにする。

### 当てにならないときは並べない (2026-09-25 追記)

実験は、前の文章が 200 文字あり、候補が 7 個の場合しか測っていない。
その外では、言語モデルが辞書の順より悪くなりやすい。

- **前後の文章がほとんど無いとき。** 行の頭や「。」の直後などである。
  採点が「文脈抜きで、ありふれた短い文字列か」になる。辞書の順の重みは
  1 位と 2 位で 0.69 しか差がなく、手がかりが無いまま辞書の順が崩れる。
- **候補が多いとき。** `ln(順位)` は後ろのほうでほとんど差がつかない
  (10 位と 100 位で 2.3)。候補が多いほど、たまたま良い点を取る外れも
  出やすい。後ろの候補を位置で覚えて選ぶ打ち方も崩れる。

そこで次のようにする。どちらも設定で変えられ、意味も分かりやすい。

- **辞書の上位 `top` 個 (既定 7) だけを並べ替える。** 残りは辞書の順で
  後ろに付ける。遅延の上限もこれで決まる。
- **前後の文章が、句読点・記号・空白を除いて `min_context` 文字 (既定 2)
  に満たなければ並べ替えない。**

文脈の効き目だけを測る採点 (文脈ありの対数尤度から文脈なしの対数尤度を
引く) も考えた。筋は良いが、珍しい候補を持ち上げすぎないかを測って
からにする。

A を採らないのは、往復が増えるうえ、並べるのに要る情報 (学習の履歴) が
サーバにあるから。C を採らないのは、言語モデルならデータも学習も要らず、
実験で十分な精度と速さが出たから。

## 帰結

- 変換の遅延に言語モデルの計算が乗る。llm-jp-3-150m で 20 ms 前後、440m で
  70 ms 前後を見込む。**大半は前の文章 (200 文字) の計算で**、候補の採点は
  150m なら数 ms である。締め切りを越えれば辞書の順に戻るだけである。
- サーバのメモリはモデルぶん増える (Q4_0 で 84 MB または 242 MB)。
- **モデルは裏のスレッドで読み込む。** 読み込みには 0.3〜0.7 秒ほど、
  ログオン直後ならもっとかかり、答えるスレッドで行うと、そのあいだ
  どのアプリの頼みも待たされる (ADR-0032)。読み終わるまでは辞書の順で
  答える。サーバが起きた直後から変換できることを優先する。
- サーバは一度に一つの要求しか捌かないので、採点のあいだ他のアプリの
  問い合わせは待つ。
- モデルと llama.cpp の DLL を配る手段が要る。辞書と同じく取得させるか、
  同梱するかはまだ決めていない。
- llama.cpp の版を上げるときは、FFI の構造体を合わせ直す必要がある。
- 周辺テキストが TIP からサーバへ渡るようになる。これまでパイプを流れたのは
  読みだけだった。

見直すきっかけ:

- 変換の遅延が気になるようになったら、▽ に入った時点で前の文章を先に送り、
  KV キャッシュを作っておく。Space の後に残るのは候補の採点だけになる。
  前の文章を短くしても精度が保てるなら、それも効く。表示した後に、
  まだ見せていない候補だけを並べ替える道も考える。
- 補完 (ADR-0019) も同じ仕組みで並べられる。▽ のあいだ前の文章は変わらない
  ので、前の文章の計算は一度で済む。いまの補完はほとんど候補が一つなので
  後回しにする。
