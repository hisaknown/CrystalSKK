# ADR-0043: 候補はかな漢字変換のモデル jinen で、読みを条件に採点して並べる

- ステータス: Accepted (並べ方は ADR-0044 で改めた)
- 日付: 2026-11-15
- 関連: ADR-0030, ADR-0031, ADR-0036

## 背景

ADR-0030 では、汎用の言語モデル llm-jp-3-150m に「前の文章 + 候補 + 後ろの
文章」の自然さを採点させて候補を並べている。使ってみると、先頭は当たるが
**2 位以下の並びがおかしい**(「状態」の次に「情態」、「度」の次に「怒」)。
評価が第一候補の正解率しか見ていなかったので、これに気づけなかった。

[jinen](https://huggingface.co/togatogah/jinen-v2-xsmall.gguf) は、かな漢字変換
のためだけに学習した小さなモデルである (qwen3、35.7M パラメータ、GGUF で
配布)。`U+EE02 前の文章 U+EE00 読み U+EE01 変換結果 </s>` の形を学んでいて、
読みはカタカナで渡す (v2 のモデルカードには書かれておらず、v1 のカードにある。
ひらがなで渡すと崩れた出力になる)。後ろの文章は受け取らない。
ライセンスは CC BY-SA 4.0 で、学習データの一部に国立国会図書館の書誌データを
使っている旨の表示が要る。

ブランチ `experiment/llm-ranking` の `score_jinen.py` で、ADR-0030 と同じ
1000 問 (このリポジトリの文章、送りなし、候補 7 個、CPU 8 スレッド) で比べた。
「τ」は、正解を除いた残りの候補の並びと L 辞書の並びとの Kendall τ で、
2 位以下がどれだけ常識的に並んでいるかの目安である (L 辞書の順は正解ではない
が、長年の編集で整えられた頻度の順ではある)。

| モデル | 大きさ | 前の文章 | λ | 第一候補の正解率 | τ | 前の文章の計算 |
|---|---|---|---|---|---|---|
| 辞書の順のまま | – | – | – | 0.887 | – | – |
| llm-jp-3-150m Q4_0 | 84 MB | 200 文字 | 0 | 0.939 | +0.375 | 16 ms |
| 〃 | | | 1 | 0.948 | +0.457 | |
| 〃 | | | 2 | 0.949 | +0.532 | |
| jinen Q8_0 | 39 MB | 64 文字 | 0 | 0.931 | +0.477 | 5 ms |
| 〃 | | | 1 | 0.933 | +0.529 | |
| 〃 | | | 2 | 0.930 | +0.576 | |
| 〃 | | 200 文字 | 1 | 0.910 | +0.513 | 13 ms |

- モデルそのものの並び (λ=0) は jinen のほうが常識的である。汎用モデルは
  大きくなるほど第一候補は当たるが、2 位以下はむしろ崩れる
  (sarashina2.2-0.5b で τ +0.31)。
- jinen は前の文章が長いと悪くなる。短い文脈で学習しているためとみる。
- 第一候補の正解率は 1〜2 ポイント下がる。問題が技術文で、一般の文章で学んだ
  jinen には不利な分野ではある。
- Q5_K_M (28 MB) と Q8_0 は精度がほぼ同じで、Q8_0 のほうが少し速い。

## 選択肢

### A. llm-jp-3-150m のまま、辞書の順の重みを上げる

- 利点: 変えるのは既定値だけで済む。λ=3 で第一候補 0.944、τ +0.593。
- 欠点: 重さは変わらない。モデル一式を自前で変換・公開する手間
  (ADR-0036) も残る。

### B. jinen に替える

- 利点: 前の文章の計算が 16 ms から 5 ms に、モデルが 84 MB から 39 MB に
  なる。「この読みなら、どの表記か」を直接測るので、採点の意味がはっきり
  する。GGUF と `tokenizer.json` がそのまま配られているので、変換・公開の
  手間が消える。
- 欠点: 第一候補の正解率が 1〜2 ポイント下がる。後ろの文章を使えない。
  作り手が一人で、更新が止まるかもしれない。

## 決定

**B を採る。**

- **プロンプトは `U+EE02 前の文章 U+EE00 読み U+EE01` とし、各候補の
  「変換結果 `</s>`」の確率で採点する。** `U+EE01` までは全候補で共有する。
  読みはカタカナにし、送りありなら送り仮名まで含める (`おくr` + `り` →
  `オクリ`)。候補にも送り仮名を付ける。NFKC への正規化は語彙が持っている。
- **後ろの文章は使わない。** 設定から `ranker.after` を除き、TIP も読まない。
  ふつうは末尾に書き足していくので、失うものは小さい。パイプの要求には
  後ろの文章の欄が残っている (空で送る)。
- 既定は前の文章 64 文字、`weight` 2.0 とする。
- **モデルは Hugging Face から、版 (コミット) を固定して導入のときに取得する。**
  ADR-0036 の「自前で変換して Release に置く」はやめ、`tools/ranker-model` を
  除く。ハッシュを確かめ、知らないものは置かない点は変えない。
  こちらから再配布しないので、ライセンスについては README にクレジットと
  出典の表示を書けば足りる。取得できない環境向けに `--ranker-from` は残す。
- 量子化は Q8_0 を使う。

A を採らないのは、軽さと配布の手間で B が大きく勝ち、2 位以下の並びは
同じ第一候補の正解率で比べると B のほうが良いからである。

## 帰結

- 変換の遅延と、サーバのメモリが減る。
- 第一候補の正解率は少し下がる。最後に使った語は先頭から動かさない決まり
  (ADR-0030) があるので、使い続けるうちに差は目立たなくなるとみる。
- 以前の一式にだけあった `LICENSE` と `NOTICE.md` は、導入のときに片付ける。
- モデルの版を上げるときは、`crystalskk-setup` の版とハッシュを替える。
  プロンプトの形が変わる版 (jinen v3 など) なら採点も直す。

見直すきっかけ:

- jinen の取得元が消えた、または更新が止まって困ることが出てきたら、
  ADR-0036 のように自前で置く。
- 後ろの文章が効く場面 (文の途中を直す打ち方) が多いと分かったら、汎用の
  モデルとの併用を考える。
- 評価は第一候補の正解率に加え、τ (2 位以下の並び) と「辞書の先頭の正解を
  動かした数」も見る。
