## 1. 背景と目的

Windows における SKK 方式の日本語入力には、複数の先行実装がある。

| 実装 | 方式 | 特徴 |
|---|---|---|
| skkime | TSF TIP | 初期から存在する実装 |
| SKKFEP (SKK日本語入力FEP) | TSF TIP | フロントエンド／バックエンドのプロセス分離。SandS、動的補完、予測変換などの独自拡張。COM 経由のスクリプト連携 (SKKGate)。ソース非公開 |
| CorvusSKK | TSF TIP | SKK 標準機能の網羅性が高い。OSS |

いずれも実用水準にあり、CrystalSKK はこれらを置き換えることを目的としない。その上で、新規に作る意義は次の3点に置く。

- **カスタマイズ経路の設計**: SKK はユーザーごとの調整項目が本質的に多く、GUI 設定だけでは表現しきれない。先行実装でも、設定画面を持たずスクリプト連携で拡張性を確保する (SKKFEP/SKKGate)、あるいは設定項目を増やし続ける、という異なる解が採られている。CrystalSKK は「宣言的設定」と「スクリプト拡張」を最初から二層として設計し、どちらかに寄せない。
- **拡張の土台**: 候補の並び替え、補完、文脈を踏まえた提示といった「賢さ」を後から足せる構造を、初版の時点で用意する。先行実装の優れた拡張機能 (SKKFEP の動的補完・予測変換など) は、後付けではなく設計に織り込まれた形で提供したい。
- **保守性とビルドの容易さ**: C/C++ ツールチェインの煩雑さが、コントリビューションと長期保守の障壁になっている。`cargo build` のみで完結するビルドを維持する。

なお、先行実装から学ぶべき設計判断として、**SKKFEP が既にフロントエンド (TIP) とバックエンド (辞書プロセス) を分離している**点は重要である。CrystalSKK も同様のプロセス分離を採るが (§7)、これは独自の着想ではなく、TSF TIP が全アプリケーションのプロセス内で動作するという制約から導かれる自然な帰結であると理解しておく。

### 目的 (Goals)

1. Windows 上で、既存 SKK ユーザーが違和感なく移行できる素直な SKK 実装を提供する。
2. 設定を「宣言的な TOML」と「スクリプトによる拡張」の二層に分け、カスタマイズの天井を取り払う。
3. 変換パイプラインを拡張可能な構造にし、将来の賢い候補提示・補完の土台とする。
4. C ツールチェインを要求しない、`cargo build` だけで完結するビルドを維持する。

- SKK日本語入力FEP — http://coexe.web.fc2.com/skkfep.html

## 2. ターゲットユーザー

| # | ペルソナ | 状況 | CrystalSKK に求めるもの |
|---|---|---|---|
| P1 | 既存 SKK ユーザー | Emacs/ddskk や AquaSKK を日常的に使い、Windows でも同じ入力がしたい | 素直な SKK 挙動、ユーザー辞書の可搬性 |
| P2 | Windows の SKK ユーザー | CorvusSKK / SKKFEP を使っているが細かい不満がある | 移行のしやすさ、細かい調整が効くこと |
| P3 | カスタマイズ志向の開発者 | 自分の入力環境を作り込みたい | スクリプトによる拡張点、読みやすいコードベース |
| P4 | SKK 未経験者 | SKK に興味はあるが敷居が高い | 導入のしやすさ、既定値のまま使えること |

v1.0 の主対象は **P1・P2・P3**。P4 は「既定値で破綻しない」ことを担保するに留め、積極的な獲得は目指さない。

## 3. 設計原則

これらは機能の取捨選択が割れたときの判断基準とする。上にあるものほど優先する。

1. **入力を止めない** — いかなる拡張・障害・辞書の状態であっても、打鍵に対する応答が遅延・停止してはならない。壊れた拡張は無効化して素の挙動で続行する。
2. **ホストアプリを巻き込まない** — IME の不具合が入力先アプリのクラッシュやハングになってはならない。
3. **ユーザーのデータはユーザーのもの** — 入力内容を外部に送信しない。学習データはローカルに、可搬な形式で保持する。
4. **逃げ道を常に用意する** — GUI で届かない設定は TOML で、TOML で届かない設定はスクリプトで到達できる。
5. **SKK の驚きのなさを守る** — 賢さは既定の SKK 挙動を壊さない範囲で足す。予測が外れても、SKK として期待される動作に落ちる。

## 4. スコープとマイルストーン

### v0.1 — 変換エンジン単体（core） ✅ 2026-09-22

TSF に触れず、ライブラリとして SKK の変換を完結させる。

- ローマ字かな変換（AZIK 等の別テーブルを差し替え可能な構造）
- 入力モード: ひらがな / カタカナ / 半角カタカナ / 全角英数 / Ascii
- 変換状態機械: 確定入力（■）/ 見出し語入力（▽）/ 候補選択（▼）
- 送り仮名あり変換、送り仮名なし変換
- abbrev モード（`/`）
- 辞書検索（静的辞書・ユーザー辞書の合成）
- 学習（MRU による候補順の更新）
- 辞書登録モード（候補がないときの再帰的な入力）
- CLI ハーネスによる手動確認と、状態機械のテストスイート

**完了条件**: キー列を入力し、確定文字列と表示状態（preedit / 候補リスト）が期待通りに得られることがテストで示されている。

### v0.2 — TIP スケルトン ✅ 2026-09-22

- TSF TIP としての登録・解除、言語バーへの表示
- キーイベントの取得と composition への反映
- x64 でのみ動作すればよい
- 候補ウィンドウは仮実装（最低限の Win32 ウィンドウ）

**完了条件**: メモ帳で「かんじ」と打って「漢字」が確定できる。→ 達成。ただし候補ウィンドウは未着手で、候補は Space で一つずつ送る形。表示属性 (下線) も未実装。

### v0.3 — 実用最小（Daily Driver）

- サーバープロセス分離と IPC
- 辞書のダウンロードとインデックス化
- ユーザー辞書の永続化（SKK 標準テキスト形式）
- 候補ウィンドウの本実装（ラベル選択、注釈表示、DPI・ダークモード対応）
- `config.toml` による設定
- x86 / ARM64 ビルド、AppContainer 対応

**完了条件**: 作者が他の IME を無効化して1週間使い続けられる。

### v1.0 — 公開版

- 設定スクリプト（拡張ポイントの確定と文書化）
- 動的補完と予測変換（入力体験の質に関わる機能を優先する）
- 署名済みインストーラ
- 設定 GUI（`config.toml` の薄いフロントエンド）
- ユーザー向けドキュメント一式

SKK 標準機能の網羅（数値変換、skkserv、文字コード入力など）は v1.0 の要件に含めない。網羅性は CorvusSKK が既に高い水準で提供しており、CrystalSKK が同じ土俵で張り合う意味が薄いため。必要になった時点で個別に足す。

**完了条件**: 未経験者がインストーラを実行し、案内に従うだけで日本語入力ができる。

### v2.0 — 賢い候補提示（方向性のみ）

- 前後文脈を用いた候補の並び替え
- 入力履歴に基づく n-gram ランキング
- 送り仮名・変換履歴からの予測提示

この段階の設計は v1.0 時点では確定させない。ただし **v0.1 の時点で候補ソースとランカーの分離だけは済ませておく**（§7 参照）。

## 5. 機能要件

### 5.1 必須（v1.0 まで）

| ID | 要件 |
|---|---|
| F-01 | ローマ字かな変換。変換テーブルは差し替え可能 |
| F-02 | 入力モード: ひらがな・カタカナ・半角カタカナ・全角英数・Ascii と、その相互遷移 |
| F-03 | 送り仮名なし変換（`▽かんじ` → `▼漢字`） |
| F-04 | 送り仮名あり変換（`▽おく*り` → `▼送り`） |
| F-05 | abbrev モード（`/` による英単語見出し変換） |
| F-06 | 候補選択: 次候補・前候補、ラベルによる一括選択、インライン表示と候補一覧の切り替え |
| F-07 | 辞書登録モード。候補が尽きたとき再帰的に入力して辞書に登録 |
| F-08 | 学習（確定した候補を先頭に移動）とユーザー辞書への永続化 |
| F-09 | ユーザー辞書は SKK 標準テキスト形式で読み書きする |
| F-10 | 静的辞書の web からの取得・更新・整合性検証。取得元は設定に並べ、辞書サーバが取得と更新の確認を行う (ADR-0022) |
| F-11 | 補完（見出し語の前方一致による補完） |
| F-18 | 動的補完（入力中に辞書全体から候補を提示する） |
| F-19 | 予測変換（確定前の状態から次に入力しうる語を提示する） |
| F-13 | 候補の注釈（`;` 以降）の表示。**済** (ADR-0027)。窓にだけ出し、入力欄には出さない |
| F-14 | `config.toml` による設定（キーバインド、辞書、表示、動作）。既定値は持たず、ファイルに書かれた値だけが効く (ADR-0020)。補完と候補一覧の項目から始め、キーバインドは未着手 |
| F-15 | 設定スクリプトによる拡張（拡張点は §5.3） |
| F-16 | 設定 GUI（`config.toml` を編集するフロントエンド） |

### 5.2 任意（優先度低、v1.0 に必須ではない）

- 数値変換（`#` を含む見出し語の数値展開）
- skkserv プロトコルによる外部辞書サーバー参照
- コード入力（Unicode コードポイント・JIS コードによる入力）
- 全角/半角の相互変換、ひらがな⇄カタカナ変換の確定時操作
- 複数辞書の優先度つき合成 — **済** (ADR-0022)。並べた順が優先度
- 入力履歴の統計表示

### 5.3 設定スクリプトの拡張点（v1.0 時点で公開する範囲）

| フック | 用途 |
|---|---|
| `romaji_rules()` | ローマ字テーブル。**差分ではなく表全体を返す** (ADR-0021: ファイルが表のすべてであり、元になる表を持たない) |
| `on_candidates(query, candidates) -> candidates` | 候補の並べ替え・絞り込み・追加 |
| `on_commit(yomi, word)` | 確定時の副作用（独自学習など） |
| `on_mode_change(mode)` | モード変化の通知 |

拡張点は**追加のみ可能で、一度公開したものは互換を保つ**。実行は常にサーバープロセス内で行い、各フックには実行時間の上限を設ける（§6）。

## 6. 非機能要件

| ID | 要件 | 基準 |
|---|---|---|
| N-01 | 入力応答性 | 打鍵から preedit 更新までの所要時間が p99 < 16ms |
| N-02 | 辞書検索速度 | 1回の見出し語検索が p99 < 5ms |
| N-03 | 拡張の隔離 | スクリプトのフックは実行時間上限（既定 5ms）を超えたら中断し、当該フックを無効化して通知。入力は素の挙動で継続する |
| N-04 | プロセス隔離 | 変換エンジンの異常終了が入力先アプリに波及しない |
| N-05 | メモリ | 入力先アプリに常駐する TIP 側の追加メモリが 10MB 未満 |
| N-06 | 起動 | サーバー起動から入力受付可能になるまで 1 秒未満（辞書の初回インデックス化を除く） |
| N-07 | プライバシー | 入力内容・学習データを外部に送信しない。外部通信は辞書の取得・更新に限る |
| N-08 | ビルド | C/C++ ツールチェインを要求しない。依存ツリーに `cc` crate が現れないことを CI で検証する |
| N-09 | 辞書の堅牢性 | 辞書ファイルの破損・欠損時も入力自体は継続できる |
| N-10 | 可搬性 | ユーザー辞書は他の SKK 実装で読み書きできる |

## 7. アーキテクチャ方針

確定した決定は ADR として `docs/adr/` に記録する。本節は概要のみ。

### プロセス構成

```
入力先アプリ (Word / Chrome / UWP ...)
  └─ CrystalSKK TIP (DLL, in-proc)   … キー入力、preedit 表示、候補ウィンドウ描画
        │  IPC (名前付きパイプ)
CrystalSKK Server (ユーザーセッション常駐)
        │  … 変換エンジン、辞書、学習、設定スクリプト実行
CrystalSKK Config (設定 GUI, 独立プロセス)
```

分離の理由: AppContainer からの辞書 I/O、ユーザー辞書の単一書き手の保証、大きな辞書のメモリ共有、クラッシュ隔離、ユーザースクリプトの隔離。

### クレート構成（予定）

- `crystalskk-core` — 変換状態機械、ローマ字変換、候補処理。OS 非依存・純粋ロジック
- `crystalskk-dict` — 辞書の取得・インデックス・検索・ユーザー辞書の永続化
- `crystalskk-server` — IPC サーバー、設定読み込み、スクリプト実行
- `crystalskk-tip` — TSF TIP（cdylib）
- `crystalskk-config` — 設定 GUI

### 将来の拡張のための構造（v0.1 から用意する）

候補の生成と並び替えを分離し、双方を追加可能にする。

- **CandidateSource**: 静的辞書 / ユーザー辞書 / skkserv / 補完 /（将来）予測
- **Ranker**: MRU /（将来）n-gram、文脈スコアリング
- **Context**: 直前の確定履歴、入力モード、（取得できる場合）カーソル前後のテキスト、アプリ識別子

`Context` は取得できない環境があることを前提とし、欠損時のフォールバックを常に持つ。

## 8. 非目標（Non-Goals）

- SKK 以外の入力方式（連文節変換を前提とした一般的な IME）の提供
- Windows 以外のプラットフォーム対応（ただし `core` は OS 非依存に保つ）
- ddskk の Emacs Lisp 設定の互換実行
- クラウドサービスとの連携、サーバーサイドでの変換
- 辞書そのものの同梱・再配布
- 音声入力・手書き入力

## 10. ライセンスと配布

- **コード**: MIT License
- **辞書**: 同梱しない。初回起動時に設定 UI からユーザーの操作でダウンロードする。辞書のライセンス（SKK-JISYO.L 等は GPL 系）は取得元のものに従い、その旨を UI 上で明示する
- **配布形態**: 従来型インストーラ（MSI もしくは Inno Setup）。MSIX は TIP 登録の制約により採用しない
- **署名**: v1.0 の公開にはコード署名を行う（SmartScreen 対策）

## 11. 成功指標

定量的な利用者数は目標としない。代わりに以下をもって成功とする。

1. 作者が他の IME を併用せず CrystalSKK のみで日常業務を行えている（v0.3）
2. 既存 SKK ユーザーが、ユーザー辞書を持ち込んで設定変更なしに移行できる（v1.0）
3. 外部のコントリビューターが、リポジトリを clone して `cargo build` のみでビルドできる（全期間）
4. 「入力が固まる」「アプリが落ちる」の報告が継続的に発生していない（v1.0 以降）

| Q-08 | 先行実装の独自拡張をどこまで取り込むか | 動的補完・予測変換は v1.0 に入れると決めた (2026-09-22)。SandS、偽装確定、母音未確定状態での予測は未定。§3 の「驚きのなさ」との兼ね合いで、既定 on/off を含めて判断する |
